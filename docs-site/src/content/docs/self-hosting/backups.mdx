Spanlight backs up its Postgres database to your own object storage. This page covers what a backup contains, how to switch the nightly job on, how to take a backup on demand, and how to rehearse a restore. The full restore procedure is the [restore runbook](/docs/runbooks/restore/).

The commands use this shortcut. Run it from the repository root:

```bash
spl() { docker compose -f deploy/compose.yaml --env-file deploy/.env "$@"; }
```

If you start the stack with extra files, such as `deploy/compose.minio.yaml`, add the same `-f` options.

## What is backed up

A backup is one `pg_dump` of the whole `spanlight` database in custom format (`-Fc`). It contains traces, spans, users, projects, API key hashes, prompts, datasets, alert rules and the job queue.

A backup leaves out:

- Rate-limit buckets. They are an unlogged table with short-lived counters that refill on their own.
- Anything outside the database. That means the contents of the bucket other than backups, your environment variables, and `CREDENTIALS_KEYS`.

<Aside type="caution">
Back up `CREDENTIALS_KEYS` and your `deploy/.env` file separately, in a secret manager. Encrypted values in a restored database, such as two-factor secrets and provider credentials, cannot be read without the key, and a lost key cannot be recovered.
</Aside>

A dump holds every prompt and completion your applications sent. Keep the bucket private and encrypted at rest. Each upload asks the store for server-side encryption with `BACKUP_S3_SSE` (default `AES256`); set it blank for a store that rejects it, such as MinIO without a KMS (`deploy/compose.minio.yaml` does).

## Turn on nightly backups

The worker runs the backup job once a day, from 03:00 UTC. If the worker was down at that time, the day's job runs as soon as a worker starts. A job gets up to three attempts. It uploads the dump to `backups/YYYY/MM/DD/spanlight-<UTC timestamp>.dump` in your bucket.

The job runs only when all of this is true:

- Object storage is configured: `BACKUP_S3_BUCKET`, `BACKUP_S3_ACCESS_KEY` and `BACKUP_S3_SECRET_KEY` are all set. Add `BACKUP_S3_ENDPOINT` for a store other than AWS, and `BACKUP_S3_REGION` for an AWS bucket. MinIO and most self-hosted stores also need `BACKUP_S3_FORCE_PATH_STYLE=true`. Setting only some of them stops the application at start-up.
- `BACKUP_DATABASE_URL` is set.
- `BACKUPS_ENABLED` is not `false`. It is `true` by default.

If any of these is missing, the job ends as `skipped_not_configured` and takes no backup. It does not fail, so nothing alerts you. Check it yourself (see below).

`BACKUP_DATABASE_URL` must name a superuser or a role with `BYPASSRLS`. The tenant tables force row-level security, and a dump made by the application role fails instead of producing an incomplete backup. On the bundled Postgres, the `postgres` owner qualifies. The Compose file passes `BACKUP_DATABASE_URL` to the worker only, because it is a role that bypasses row-level security and the API faces the network. On a managed Postgres, create a `BYPASSRLS` role for it.

Add the settings to `deploy/.env`:

```bash
BACKUP_S3_BUCKET=my-spanlight-backups
BACKUP_S3_ACCESS_KEY=...
BACKUP_S3_SECRET_KEY=...
BACKUP_S3_REGION=eu-west-1
BACKUP_DATABASE_URL=postgresql://postgres:<POSTGRES_PASSWORD>@postgres:5432/spanlight
```

Then recreate the services that read them:

```bash
spl up -d worker
```

Set a lifecycle rule on the bucket that aborts incomplete multipart uploads after one day (`AbortIncompleteMultipartUpload` with `DaysAfterInitiation: 1`). A crash in the middle of a backup can leave uploaded parts behind, and they cost storage until the rule removes them.

### Retention

Backups never prune from the worker. Schedule `spanlight backup prune --apply` daily after backup completion with a separate operator-only List/Delete principal supplied through `BACKUP_S3_*`. Preview first with `spanlight backup prune`. It preserves newest per each of the last 14 UTC days, newest per each of eight Sundays, newest overall, future-dated and unknown keys. Listing or any deletion failure exits nonzero. Without the separate schedule, uploads continue and storage grows. Do not substitute a generic 56-day expiration. Pause retention during recovery. See the [retention and credential migration runbook](/docs/runbooks/restore/#credential-isolation-and-retention).

### Try it with MinIO

To try backups without a cloud account, add the MinIO file. It starts a local MinIO server, creates the bucket and points the `api` and `worker` at it:

```bash
docker compose -f deploy/compose.yaml -f deploy/compose.minio.yaml --env-file deploy/.env up -d
```

You still need `BACKUP_DATABASE_URL`. The local defaults are public. MinIO provisions separate export/upload/recovery/retention users; API and worker receive no root keys. Override all `MINIO_*_USER` and `MINIO_*_PASSWORD` values in `deploy/.env` if anyone else can reach the host. The ports are bound to `127.0.0.1`. See [Configuration](/docs/configuration/#minio-variables) for the variables. For production, use a real bucket instead.

Recovery listing/restoring needs a separate List/Get principal in a protected operator environment file. Routine upload-only workers cannot list or restore. Restore accepts only the current accessible object, without a version selector. Upload-only credentials still permit overwriting the same key; this is not immutability. Preserve historical backups and keyring entries, and verify a new restore before revoking legacy permissions.

## Take a backup now

```bash
spl exec worker spanlight backup now
```

On success it prints the key and size:

```text
Backed up to backups/2026/10/09/spanlight-20261009T143012Z.dump (48213377 bytes).
```

It needs object storage and `BACKUP_DATABASE_URL`. `BACKUPS_ENABLED` only governs the nightly job, so it does not stop a backup you ask for. Retention runs only through the separate operator command and schedule.

If a setting is missing, the command exits with status 1 and names it:

```text
Error: BACKUP_DATABASE_URL is not set
Error: backup storage is not configured (set BACKUP_S3_BUCKET, BACKUP_S3_ACCESS_KEY, BACKUP_S3_SECRET_KEY)
```

List the backups, oldest first:

```bash
docker run --rm --network <compose-network> --env-file <recovery.env> <deployment-image> spanlight backup list
```

Each line is the key, the size in bytes and the upload time. It prints `No backups found.` when the bucket holds none.

## Check it worked

Do not assume the nightly job works. Check it after you set it up, and now and then afterwards.

```bash
docker run --rm --network <compose-network> --env-file <recovery.env> <deployment-image> spanlight backup list
spl logs --since 24h worker | grep -E 'backup_completed|backup_skipped|backups?_prune'
spl exec postgres psql -U postgres -d spanlight -c \
  "SELECT status, outcome, attempts, last_error, created_at
     FROM jobs WHERE kind = 'backup_database' ORDER BY id DESC LIMIT 3"
```

A good night leaves a `backup_completed` log line with the key, the size and the seconds it took, and a `done` row with outcome `ok`. A `backup_skipped` line gives the reason: `BACKUPS_ENABLED is false`, `BACKUP_DATABASE_URL is not set` or `object storage is not configured`. A newest backup in the list that is more than a day old is a reason to look.

## Restore

A restore always goes into a new, empty database. `spanlight restore` refuses a database that already has any table, view, sequence or foreign table outside the system schemas, so it cannot overwrite live data. It streams the dump from object storage into `pg_restore --no-owner --no-privileges --single-transaction`, so a failure leaves the target empty.

```bash
spanlight restore --key backups/2026/10/09/spanlight-20261009T030000Z.dump
```

The target comes from the `RESTORE_TARGET_URL` environment variable. Prefer that to the `--target-url` option, because a URL on the command line is visible in the process list and your shell history. The dump has neither owners nor privileges, so after a restore you run `spanlight ensure-app-role` against the restored database so the API and worker can connect, and then `spanlight restore-reconcile prepare`, `apply` and `check` before any service starts: a restored database still holds jobs that were running, notifications about to be sent and schedules that would fire again. The [restore runbook](/docs/runbooks/restore/) has the complete procedure, including how to swap the restored database in for the live one and how to go back.

### Erasures and backups

A dump holds whatever the database held when it was taken. Data you removed later with an [end-user erasure](/docs/guides/privacy/#erase-one-end-users-data) stays in every backup taken before the erasure until that backup is pruned: up to 14 days for a daily backup and up to 8 weeks for a Sunday one. Keep the bucket access-restricted, and when you restore a backup, run again every erasure requested after the backup was taken. A restored audit log does not know about those requests, because they came later, so keep your own log of erasure requests (or [stream the audit log](/docs/audit-log/) elsewhere) and work from that.

## Rehearse a restore

A backup you have never restored is a hope, not a backup. This drill restores the newest backup into a scratch database next to the live one. It does not stop the stack and does not change the live database. It needs disk space for a full copy of the data.

<Steps>

1. **Pick a backup.**

   ```bash
   docker run --rm --network <compose-network> --env-file <recovery.env> <deployment-image> spanlight backup list
   ```

   Choose a key, usually the newest. The one-off image receives the operator recovery environment file, including the separate List/Get credentials.

2. **Create an empty scratch database.**

   ```bash
   spl exec postgres psql -U postgres -d postgres -c 'CREATE DATABASE spanlight_drill'
   ```

3. **Restore into it.** The URL uses the owner password from `deploy/.env`, read by the shell so it never appears on the command line:

   ```bash
   export RESTORE_TARGET_URL="postgresql://postgres:$(sed -n 's/^POSTGRES_PASSWORD=//p' deploy/.env)@postgres:5432/spanlight_drill"
   sudo install -d -m 700 -o "$(id -u)" -g "$(id -g)" /srv/recovery
   docker run --rm --user "$(id -u):$(id -g)" --network <compose-network> --env-file <recovery.env> -e RESTORE_TARGET_URL \
     -v /srv/recovery:/recovery <deployment-image> \
     spanlight restore --key backups/2026/10/09/spanlight-20261009T030000Z.dump --receipt /recovery/receipt.json
   unset RESTORE_TARGET_URL
   ```

   This assumes `POSTGRES_PASSWORD` has no characters that need escaping in a URL. The command ends with `Restored <key>: <bytes> bytes, sha256 <digest>.` and a reminder to run `ensure-app-role` and then `restore-reconcile prepare`. The `-v` mount keeps the receipt in `/srv/recovery` on the host after the container exits. The image runs as its own unprivileged `app` user, which cannot write a root-owned directory, so the first line creates `/srv/recovery` for your account and `--user` runs the container as that account. This drill checks the data only; to rehearse the whole recovery, including the quarantine of restored work, follow the [restore runbook](/docs/runbooks/restore/) against the scratch database instead.

4. **Check the data.**

   ```bash
   spl exec postgres psql -U postgres -d spanlight_drill -c \
     "SELECT 'traces' AS table_name, count(*) FROM traces
      UNION ALL SELECT 'spans', count(*) FROM spans
      UNION ALL SELECT 'projects', count(*) FROM projects"
   spl exec postgres psql -U postgres -d spanlight_drill -tA -c "SELECT max(started_at) FROM traces"
   spl exec postgres psql -U postgres -d spanlight_drill -tA -c "SELECT version_num FROM alembic_version"
   ```

   The counts should be close to the live database, the newest trace should be about as recent as the backup, and the revision should match the version that took the backup.

5. **Remove the scratch database.**

   ```bash
   spl exec postgres psql -U postgres -d postgres -c 'DROP DATABASE spanlight_drill'
   ```

</Steps>

Time the drill. How long it took tells you how long a real restore will keep you down.

## Troubleshooting

- **The job ends as `skipped_not_configured` and no backup appears.** A `backup_skipped` log line names the missing piece: `BACKUPS_ENABLED is false`, `BACKUP_DATABASE_URL is not set` or `object storage is not configured`. See [Turn on nightly backups](#turn-on-nightly-backups).
- **`Error: BACKUP_DATABASE_URL is not set`, or `Error: backup storage is not configured (set BACKUP_S3_BUCKET, BACKUP_S3_ACCESS_KEY, BACKUP_S3_SECRET_KEY)`, from `backup now`.** Set the named variables in `deploy/.env` and run `spl up -d worker`.
- **The dump fails with `pg_dump exited with status …`.** A role without `BYPASSRLS` cannot dump the tenant tables, and the job fails instead of writing a partial backup. Point `BACKUP_DATABASE_URL` at the `postgres` owner or a `BYPASSRLS` role.
- **The newest backup is more than a day old.** The worker may be down, or the job failed three times. Read the `jobs` row's `last_error` from the query in [Check it worked](#check-it-worked), and see [The worker is not running](/docs/troubleshooting/#the-worker-is-not-running).
- **`the target database already has N relation(s) outside the system schemas; restore into a new, empty database`.** `spanlight restore` never overwrites. Create a new database and point `RESTORE_TARGET_URL` at it.
- **`no backup with key '…'`.** The key is wrong. Copy it from `spanlight backup list`.
- **The API cannot connect to the restored database.** The dump has no owners or privileges. Run `spanlight ensure-app-role` against it, then reconcile with `spanlight restore-reconcile` before starting services.
- **Two-factor secrets or provider credentials in a restored database cannot be read.** They are encrypted with `CREDENTIALS_KEYS`. Restore the key you backed up separately.
