A **budget** watches how much a scope spends in a day or a month. When the spend passes the amount, Spanlight sends a `budget.exceeded` notification to the budget's [channels](/docs/alerts/#channels), and a budget set to **block** also makes the [gateway](/docs/gateway/quickstart/) refuse further calls in that scope. Manage budgets under **Budgets** in a project.

Anyone who can see the project can read its budgets; only organization **admins and owners** can create, edit or delete them. A project can have up to 50, each with up to 10 channels, and budget names are unique within the project.

## Scope and period

| Scope | `scope_id` | Spend counted |
| --- | --- | --- |
| `project` | none | All priced spans of the project |
| `gateway_key` | The id of one of the project's gateway keys | Spans produced by calls through that key |
| `user` | An end-user id, as sent in the `x-spanlight-user` header | Spans of traces for that user |
| `model` | A model name | Spans of that model. `gpt-4o` also covers snapshot names such as `gpt-4o-2024-08-06` and `gpt-4o-latest`, but not `gpt-4o-mini` |
| `metadata` | `key=value`, such as `customer_id=acme`, split at the first `=`. The value is kept exactly as you type it | Spans of traces whose [metadata](/docs/concepts/attribution/) has that value under that key |
| `trace_name` | A trace name, 1 to 256 characters (surrounding spaces are removed) | Spans of traces with exactly that name |

There are no budgets per project API key: blocking only ever happens in the gateway, and a key that sends traces with the SDK cannot be stopped.

A metadata key does not need to be [promoted](/docs/concepts/attribution/#promote-a-key) for a budget: the spend is read from the spans, not from the attribution rollups. Metadata belongs to the trace, so a key set late in a trace puts all of that trace's spans in the period under the budget. In the dialog, **Metadata** offers the promoted keys and the keys seen in the last 7 days, or takes any valid key, and **Trace name** suggests the names seen in the last 7 days. A `scope_id` that does not fit its scope is refused with `422 UNKNOWN_SCOPE`.

The **period** is a UTC calendar day (`daily`, resetting at 00:00 UTC) or a UTC calendar month (`monthly`, resetting at 00:00 UTC on the 1st). The `amount` is in US dollars, above zero, with at most four decimal places.

Spend is the cost of the priced spans in the scope since the period began. A span whose model has no known price adds nothing, so spend is a lower bound when unpriced models are in use (the **Unpriced models** list shows which). The spend of a scope that has spans but no priced span at all shows as "—", never as $0.

A budget fires when spend is **strictly above** the amount. It resolves, sending `alert.resolved`, once three consecutive minute evaluations measure spend at or below the amount, like any [alert rule](/docs/alerts/#how-evaluation-works).

## Notify or block

| Action | When the budget is exceeded |
| --- | --- |
| `notify` | Sends the notification. Nothing is blocked. |
| `block` | Sends the notification and makes the gateway answer `402 BUDGET_EXCEEDED` to calls in the scope, with no call to the provider and no cost, until the budget is no longer exceeded. The gateway checks fresh recorded history and reserves a priced estimate before forwarding; SDK ingestion cannot be stopped (below). |

The notification is the same for both. It names the budget, what was spent and the amount, and for a blocking budget it says when the period resets.

### What a block does and does not do

**The gateway checks recorded history and reserves an estimate.** Before forwarding, it counts matching history, settled calls and in-flight reservations once, including history from before budget creation or a scope edit. Concurrent calls see each other's reservations. The reservation becomes a final charge when the span is written; a late span or stored cost correction is reflected in the next admission check. This is an estimate-based admission limit, not an unconditional provider-bill cap: actual costs can exceed supported estimates, and unpriced or unmodelled inputs remain outside that guarantee.

The estimate counts the request's text (`messages`, `input`, `system`, `instructions`, `tools`; images and files are not counted) and every output token the request allows: the largest of `max_tokens`, `max_completion_tokens` and `max_output_tokens`, times `n`, at the dearest price among the model you asked for and the models the route's targets would send it to, for the requested `service_tier`. A request that sets none of them reserves 16,384 output tokens, so near the amount a call without `max_tokens` can be refused although it would have fitted. The 402 message says what is spent or in flight, what the call would add and the amount, and that a lower `max_tokens` lowers the reservation. A call to a model with no known price reserves nothing and is admitted; its spend is unknown, not zero.

**What a budget cannot stop.**

- **SDK and OTLP spend cannot be stopped.** Already committed, priced history is included in the next gateway admission check. Ingestion can still add spend independently, including while another call is being admitted. Notifications and displayed spend are evaluated every 60 seconds; an evaluated-state refusal retains its `(soft limit, measured every 60 s)` suffix.
- **A leaked provider key** used outside Spanlight never touches the gateway. Only the provider's own spend caps stop it: set a monthly limit on the provider's workspace or project as well.

- **Ingestion is never blocked.** `POST /v1/traces`, the OTLP endpoint and the SDK keep recording whatever the budgets say. A budget limits what the gateway spends, not what the dashboard may know.
- **Only the gateway blocks.** Calls that do not go through a gateway key are not stopped.
- **A reservation outlives a crash by 12 minutes.** If a call's span is never written (the API process died mid-stream), its reservation is counted at the estimate after 12 minutes and corrected to the real cost if the span arrives later.
- **A cached answer is always served.** The cache is read before the budget check; a hit costs no provider spend, so it reserves nothing and is answered even when a `block` budget is firing.
- **Metadata and trace name are matched from the call.** The gateway reads the `x-spanlight-metadata` and `x-spanlight-trace-name` headers. A call that starts a new trace has the name the trace will get, `"<surface> <model>"` with the model your client asked for, such as `chat_completions gpt-4.1-mini`. A call that joins a trace (`x-spanlight-trace-id`) and lacks either header also uses the stored trace's metadata and name, the header winning per key. That is best effort: until a span of the trace has been stored, there is nothing to read, so the first calls of a run may not match. Send the headers on every call to be sure.
- **Several budgets can match one call.** The call is refused if any enabled blocking budget that matches its project, gateway key, user, model, metadata or trace name is exceeded or cannot hold the call's estimate; the message names the one with the lowest amount.
- **A stopped worker leaves notifications and displayed state stale.** Fresh recorded history and reservations still protect priced gateway admission. A previously firing state can continue refusing calls until evaluation resumes or the period resets.
- **An edit waits for the calls being admitted.** Editing, disabling or deleting a budget waits for the gateway calls the budget is admitting at that moment, and admissions that keep arriving do not wait for the edit. If the budget stays that busy, the change answers `503 BUDGET_BUSY` with `Retry-After` after a few short tries instead of hanging; try it again once the burst has passed. The old amount applies until the edit is stored.
- **Scope and period edits preserve unresolved charges.** They return `409 BUDGET_RESERVATIONS_PENDING` while calls are pending, conservative charges cannot be reclassified, or legacy charges remain ambiguous. Eligible edits preserve call identity and admission time while reading the new scope's existing history immediately. Later timestamp corrections do not move an admitted charge to another period. Amount changes retain charges and holds.
- **Deleted spend still counts.** Daily hard budgets require at least one day of project retention; monthly budgets require 31 days. Creation or update with insufficient retention returns `422 BUDGET_HISTORY_RETENTION`. When a priced span of the current UTC month is deleted (by retention, an end-user erasure or a trace deletion), its cost is kept as money in a ledger and still counts against matching budgets, so a deletion neither hides spend nor blocks calls. Project and gateway-key budgets count deleted spend by key, and model budgets by model. User, trace-name and metadata budgets count all deleted spend of the period, because the trace that carried those fields is gone. A span stored again, or one a reservation already charges, is counted once. Telemetry deletion policies are unchanged.

Charge identity remains while its raw span exists and for at least 90 days from admission. Counter aggregates expire after 62 days. This does not extend telemetry retention. Reusing a deleted trace/span identity after both retention horizons expire is outside the deduplication guarantee.

**Upgrade compatibility:** the ledger holds only spend deleted after the upgrade. Migration 1031 marks the current period's history as unknown only for projects with evidence that priced spend of this month was already lost: retention short enough to have deleted spans of this month, an end-user erasure this month, or a retention change this month. Hard budgets of those projects refuse calls with an actionable `402` until the next UTC period; every other project admits calls normally. Previously unattributed charges are preserved conservatively and may cause over-refusal; no amounts are reset.

### The 402 response

A blocked call gets HTTP `402` in the error shape of the surface the client used, so the official SDKs raise their usual billing exceptions and do not retry. A call refused before it was forwarded says what is spent or in flight, what the call would add and the amount: `Budget "Monthly cap" would be exceeded: $49.90 spent or in flight plus $0.26 for this call is over the $50.00 limit this month; a lower max_tokens lowers the reservation.` A budget blocked by measured spend names the budget and what was spent (or, when the spend is not known, the limit that was reached), as below. See [Gateway error responses](/docs/gateway/errors/) for the common fields.

OpenAI (`/gw/v1/chat/completions`, `/gw/v1/responses`):

```json
{
  "error": {
    "message": "Blocked by a Spanlight budget: Budget \"Monthly cap\" is exhausted: $52.13 of $50.00 spent this month (soft limit, measured every 60 s).",
    "type": "insufficient_quota",
    "param": null,
    "code": "insufficient_quota",
    "spanlight_code": "BUDGET_EXCEEDED"
  }
}
```

Anthropic (`/gw/v1/messages`):

```json
{
  "type": "error",
  "error": {
    "type": "billing_error",
    "message": "Blocked by a Spanlight budget: Budget \"Monthly cap\" is exhausted: $52.13 of $50.00 spent this month (soft limit, measured every 60 s).",
    "spanlight_code": "BUDGET_EXCEEDED"
  },
  "request_id": "4f2c0a7e9b1d4c3f8a5e6d7c8b9a0f1e"
}
```

Both carry the header `X-Spanlight-Code: BUDGET_EXCEEDED`. Match on `spanlight_code`, not on the message.

### Rollover

At 00:00 UTC on the first day of a new period, a blocking budget stops blocking, even before the next evaluation has resolved it. The first evaluation of the new period resolves the budget whatever the new spend is (spend of blocked or unpriced calls is not known), and it fires again only if the new period's spend is already above the amount. The `state` of a budget in the first minute of a period shows "—" until it is evaluated.

## Read a budget's burn

Each budget's bar marks 50, 80 and 100 % of the amount; hover a mark to read it in dollars. **Show burn** opens the spend to date per UTC day since the period began, drawn against the amount, with a table view. A day whose spans were all unpriced shows "—", not $0. The same series comes from `GET /api/v1/projects/{project_id}/budgets/{budget_id}/burn`.

### Month-end forecast

For a monthly budget, the burn response also carries a forecast. The app does not show it yet.

- `forecast_usd` is the period's spend so far plus the mean spend of the last 7 complete UTC days, times the time left in the period (the rest of today included). It is the traced spend the budget measures, at the last days' rate, not a promise of the bill.
- `forecast_basis_days` is how many days that mean covers. Days that ended before the project was created are no history and are left out; every later day counts, a $0 day included. A project created this week starts at fewer than 7.
- `forecast_crosses_on` is the first UTC day the spend passes the amount: the day it did, when it already has, or the day the forecast does. It is `null` when the forecast stays under the amount until the period resets.

The forecast is `null` for a daily budget, under 3 days of history, and when any of those days had spans none of which could be priced. An unknown day is never counted as $0.

To start a budget from what is spending, open **Cost, Spend**, open a row's **…** menu and choose **Set a budget for this**. The create dialog opens with the row's trace name, user or metadata pair filled in. A link to `/budgets?new=1&scope=user&value=…` does the same (`scope` is `trace_name`, `user`, `model` or `metadata`, which also takes `key`).

## Check it worked

A budget of `$0.01` is the quickest way to see a block.

1. Create a blocking budget on the project with the amount `0.01`. A toast reads `Created budget "…"`.
2. Send calls through a gateway key, each with a `max_tokens`, until their priced cost passes `$0.01`.
3. The next call through the key is refused with `402` and `spanlight_code` `BUDGET_EXCEEDED`, before any evaluation: its message says the budget would be exceeded.
4. Within a minute the evaluation measures the spend: the budget's row shows it as `$… of $0.01` with a percent of 100 % or more, in the danger colour, and a **Blocking (soft)** badge next to the name; a gateway-key budget, where only gateway calls can spend, shows **Blocking** instead. A `block` budget's row also shows **In flight**, the gateway estimates held for calls still running, or "—" until the first evaluation.

## The weekly digest

Every **Monday at 08:00 UTC**, each organization member with a verified email address gets one message per project with a summary of the week that ended at 00:00 UTC that day (seven whole UTC days, compared with the seven before): spend, LLM calls, error rate and p95 latency with their changes, the top five models by cost, and how many alerts fired.

- **Turn it off per project** with **Weekly digest email** in project settings (admins and owners). It is on by default.
- **Quiet projects are skipped.** A project is included only when it received at least one span during the week.
- **It needs an email provider.** Without one, the digest job ends as skipped and sends nothing. Operators can switch the digest off for the whole deployment with `WEEKLY_DIGEST_ENABLED`.
- **Unknown figures show "—"** with no change, and a change against an unknown or zero earlier value reads "new". The shared demo account and the demo organization are never mailed.

If a run is interrupted, the retry sends only to projects that were not yet queued, so nobody gets a project twice.

## Settings

Budgets are evaluated by the alert evaluation job, so they follow `ALERTS_EVALUATION_ENABLED`; the digest follows `WEEKLY_DIGEST_ENABLED`. See [Alerts](/docs/alerts/#settings) and [Configuration](/docs/configuration/#alerts).

## Troubleshooting

| You see | Check |
| --- | --- |
| A blocking budget did not block | Spend sent from the SDK reaches the budget on the next evaluation, up to a minute later (see above). Check that the budget is enabled, that its scope matches the call (the gateway key id, the exact `x-spanlight-user` value, the model the client asked for or the route's resolved model, the `key=value` pair in `x-spanlight-metadata`, or the trace name), and that spend is above the amount: a model without a known price adds nothing and reserves nothing. |
| A call was refused although the spend is below the amount | The call's estimate did not fit next to the spend already settled or in flight. A request without `max_tokens` reserves 16,384 output tokens: set `max_tokens` to what the call needs. |
| Spend shows "—" | The budget has not been evaluated yet (it shows within a minute), or the scope has spans and none is priced. The tooltip on "—" says which: "Not evaluated yet. Spend shows within a minute." or "No spend measured in this period yet. It shows within a minute if the scope has priced spend." |
| Calls are blocked and you want them back now | Raise the amount, disable the budget or delete it. The scope is unblocked straight away. |
| No digest arrived | An email provider must be configured, the project's toggle must be on, the project must have had traffic that week, and your email must be verified. |
| Evaluation is late or stopped | See the [alerts runbook](/docs/runbooks/alerts/), in particular [evaluation lag](/docs/runbooks/alerts/#evaluation-lag). |
