# 17. Gateway budgets reserve before forwarding

Date: 2026-10-25 · Status: accepted · Supersedes the "blocking lags the spend" consequence of [ADR 12](0012-budget-block-reads-evaluated-state.md) for gateway calls

## Context

A `block` budget refused gateway calls only while its hidden alert rule was firing, and the rule measured the spend once a minute. Between two evaluations every call was admitted, however many ran at once, so a fast agent loop or a leaked gateway key could spend far past the cap: a $0.002 budget was measured at six times its amount before it blocked. ADR 12 accepted that lag to keep per-call sums off the hot path.

The evaluations already had the answer. A judge run reserves an estimate of its cost before calling the provider and settles the real cost afterwards ([ADR 15](0015-evaluations-through-the-gateway-with-reserved-budgets.md)), so concurrent runs see each other's reservations and cannot pass the edge together. What the gateway needed was that pattern without a `SUM` over spans or runs on every call.

## Decision

Before forwarding a call, the gateway reserves an estimate of its cost against every matching `block` budget; the span write replaces the reservation with the real cost.

- **One counter row per budget and period.** `budget_counters (budget_id, period_start)` holds the gateway spend settled this period (G) and the reservations in flight (R). With M the spend the alert evaluator last measured this period and E the call's estimate, the call is admitted when `max(M, G) + R + E ≤ amount` for every matching budget. `max(M, G)` carries a budget created or edited mid-period with no backfill: the counter starts at zero and M has the history.
- **The estimate is a ceiling.** The request's text (`messages`, `input`, `system`, `instructions`, `tools`; image, file and audio parts are not counted) at `app.pricing.tokens`' rate, plus the largest of the requested `max_tokens`, `max_completion_tokens` and `max_output_tokens` times `n` as output, or 16,384 output tokens when the request sets none, priced for the requested `service_tier` at the dearest of the model asked for and the route's targets (each with its provider, so an alias or fallback to a pricier model, and a provider's priority factor, are reserved). Token counts are clamped to the largest count the price book prices, so an absurd `max_tokens` is refused, not admitted as unknown. No priced candidate gives no estimate and the call is admitted as unknown, as ADR 12 does; a zero estimate (a $0 price override) reserves nothing.
- **Locks in budget order, commit before the call.** In the guard's short transaction under the project binding, the matching budgets are read `FOR KEY SHARE` (an edit or deletion, which locks the budget and then its counters, is waited for and re-read, and cannot start until the check commits), the counter rows are inserted if missing, locked `FOR UPDATE` in `budget_id` order (no deadlock when one call matches several budgets), checked all before any other write, then updated and one reservation row inserted per (call, budget). A refusal leaves only the zero counter rows it created. The transaction commits before the upstream call, so no connection is held while the provider answers and the next call, on any replica, sees this reservation. No advisory locks: the row lock serialises the check, as the rate limiter's does ([ADR 7](0007-postgres-backed-rate-limiting.md)).
- **The evaluated state stays the first refusal.** A budget whose rule is firing refuses the call at once, with the soft-limit message, since that spend may be the SDK's, which the gateway cannot stop. A refusal by the counter says what is spent or in flight, what the call would add and the cap, and that a lower `max_tokens` lowers the reservation.
- **Settle with the span.** The span transaction, last of all so the counter lock is held shortest, deletes the call's reservation rows and moves each amount from reserved to settled as the stored span's cost, or, when the cost is unknown, `app.evals.budget.failed_call_charge`: nothing for a call never sent or refused with an HTTP error status, else the estimate. A retry that finds no row writes nothing, so settling is idempotent. A span the recorder gives up on (a write the database refuses, a payload it cannot prepare) is settled the same way in a short transaction of its own, so the hold ends in seconds, not at the lease; a span dropped because the write backlog is full waits for the reaper, since the database is what is slow.
- **Leases and the reaper.** A reservation expires 12 minutes after the call began: the 10 minutes a stream may run after its first chunk (`STREAM_TOTAL_TIMEOUT_S`) plus the route's time to that chunk and the recorder's retries. Every minute the `reap_budget_reservations` job marks expired rows `reaped`, in batches of 500 with one transaction each, and counts them at their estimate. A late settle of a reaped row adds `charge − amount`, so the real cost wins. Reaped rows go with the settle or with the cleanup job after two months, as do old counter rows.
- **Periods and edits.** `period_start` comes from the call's clock and is stored on the reservation, so a call admitted at 23:59:59 settles into its own day. Changing a budget's scope or period drops its counters and reservations: the spend they counted belonged to the old one.
- **Observability.** `spanlight_budget_blocks_total{reason="reserved"|"firing"}`, `spanlight_budget_reserve_seconds`, `spanlight_budget_reservations_reaped_total` and the gauge `spanlight_budget_reservations_held`.

## Consequences

- **The cap is hard for gateway spend.** Under any number of concurrent calls and api replicas, the gateway spend admitted against a budget whose spend all goes through the gateway (every `gateway_key` budget) exceeds the cap by at most one estimate's error. Twenty concurrent calls on a budget sized for five admit exactly five.
- **SDK and OTLP spend is measured, not stopped.** Ingestion is never blocked, and spend that did not go through the gateway reaches the guard only through the evaluator's measurement, a minute late. For mixed traffic the guarantee is that of ADR 12 for the SDK's share; a follow-up can stamp G when M is written so gateway spend since the last evaluation counts once.
- **The estimate errs high.** A request without `max_tokens` reserves 16,384 output tokens, which near the cap refuses calls that would have fitted; the refusal names the estimate and the remedy. Images and files are not counted, so a call heavy in them under-reserves until it settles.
- **A crash counts the worst case.** A reservation whose span was never written (the api process died, or a stream was never read) is counted at its estimate after 12 minutes, until a late settle corrects it. A high reaped count means api processes are dying mid-call.
- **Two short lock sections per call that matches a block budget.** A budget's calls serialise on its counter row for the reserve and again for the settle. Calls that match no block budget make no write. The reserve histogram shows when a hot budget needs the levers in the spec: `synchronous_commit = off` on the reserve, then per-replica slices.
- **A cache hit near the cap is refused.** The reservation runs before the cache lookup, so a call that would have been answered from the cache at no cost is refused when its estimate does not fit. Reordering the two is a follow-up. So is caching the price book, which the guard loads (three queries) on every call that matches a block budget.
- **Leaked provider keys are out of reach.** A key used outside Spanlight never touches the gateway; only the provider's own spend caps stop it, and the docs say so.
